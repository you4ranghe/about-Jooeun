# 01. 요구사항 정의

> 이 문서는 설계 문서입니다. 구현 코드를 포함하지 않습니다.
> 문서 내 SQL/타입 표기는 "명세"이며 실행 대상 산출물이 아닙니다.

## 0. 이 프로젝트의 성격 규정

먼저 성격을 못 박아 두어야 뒤의 모든 판단이 흔들리지 않습니다.

- **운영자는 1명**입니다. 즉 쓰기 트래픽은 사실상 0이고, 동시성 제어·낙관적 락·감사 로그 같은
  업무 시스템의 기본기는 **의도적으로 빼야 하는** 영역입니다.
- **읽기 트래픽도 소규모**입니다(합의된 가정: 월 수백 회). 성능 최적화의 목적은 "빠르게"가 아니라
  **"무료 티어 한도를 건드리지 않기"** 입니다. 이 둘은 결론이 다릅니다.
  (예: 캐싱은 응답 속도가 아니라 *함수 호출 횟수*를 줄이려고 합니다.)
- **가용성 요구는 낮지만 신뢰성 요구는 높습니다.** 채용 담당자가 링크를 열었을 때 500이 뜨는 것은
  포트폴리오로서 치명적입니다. 반면 3초 느린 것은 거의 문제가 아닙니다.
  → 이 비대칭이 "정적 렌더링 우선" 원칙의 진짜 근거입니다. 정적 HTML은 DB가 죽어도 서빙됩니다.

### 품질 속성 우선순위 (충돌 시 위가 이깁니다)

| 순위 | 속성 | 구체적 기준 |
|---|---|---|
| 1 | 비용 = 0 | 어떤 상황에서도 유료 전환이 필요 없어야 함 |
| 2 | 비공개 데이터 미노출 | `draft` 프로젝트가 어떤 경로로도 조회되지 않을 것 |
| 3 | 공개 페이지 가용성 | Supabase가 일시정지 상태여도 공개 갤러리는 떠야 함 |
| 4 | SEO / 공유 품질 | 검색·링크 공유가 정상 동작 |
| 5 | 관리자 편의성 | 내가 쓰기 편할 것 |
| 6 | 응답 속도 | 위 다섯 개를 해치지 않는 선에서 |

> 5번(관리자 편의성)이 6번보다 위인 이유: 쓰기 흐름이 불편하면 프로젝트를 안 올리게 되고,
> 그러면 서비스 자체가 존재 이유를 잃습니다. 사이드 프로젝트의 최대 리스크는 성능이 아니라 방치입니다.

## 1. 액터 정의

| 액터 | 설명 | 인증 | 접근 범위 |
|---|---|---|---|
| **방문자 (Visitor)** | 채용 담당자, 동료 개발자, 검색 크롤러 | 익명 (`anon` 롤) | 공개(`published`) 프로젝트 읽기만 |
| **관리자 (Admin)** | 나 (단일 계정) | Supabase Auth 이메일/비밀번호 | 전체 읽기 + 전체 쓰기 |
| **시스템 (System)** | keep-alive / 백업 스케줄러 | 별도 자격증명 | 최소 권한 (상세는 `04` 참조) |

Spring 대응: `Visitor` = `ROLE_ANONYMOUS`, `Admin` = `ROLE_ADMIN`.
차이는, Spring에서는 이 구분을 `SecurityFilterChain`이 강제하지만 여기서는 **DB의 RLS가 강제**한다는 점입니다.
애플리케이션 코드는 권한 판단의 *2차 방어선*일 뿐 1차 방어선이 아닙니다.

## 2. 유스케이스

우선순위 표기:
- **P0** — 없으면 서비스가 성립하지 않음. MVP 필수.
- **P1** — MVP 범위. 없으면 쓸모가 크게 떨어짐.
- **P2** — MVP 제외. 2단계.

### 2.1 인증 / 세션 (AUTH)

#### UC-AUTH-01 · 관리자 로그인 — P0
- **액터**: Admin
- **선조건**: Supabase Auth에 관리자 계정이 사전 생성되어 있고, `app_metadata.role = 'admin'`이 부여되어 있음
- **주 흐름**
  1. `/admin/login`에서 이메일 + 비밀번호 입력
  2. Supabase Auth가 검증 후 세션 발급 (JWT access token + refresh token)
  3. 세션은 HTTP-only 쿠키로 저장
  4. `/admin`으로 리다이렉트
- **대안 흐름**: 자격증명 불일치 → 사유를 특정하지 않는 일반 오류 메시지("이메일 또는 비밀번호가 올바르지 않습니다")
- **후조건**: 이후 요청의 JWT에 `role: admin` 클레임이 실려 RLS를 통과함
- **근거**: 관리 기능 전체의 전제 조건

#### UC-AUTH-02 · 세션 유지 및 자동 갱신 — P0
- **액터**: Admin
- **설명**: access token 만료 시 refresh token으로 자동 재발급. 미들웨어가 응답 쿠키를 갱신
- **근거**: 이게 없으면 관리 화면에서 작업 중 임의로 로그아웃되어 작성 중 데이터가 날아감
- **주의**: 미들웨어 실행 범위를 관리자 경로로 한정해야 함 (근거는 `04` 함수 호출 절감 절)

#### UC-AUTH-03 · 로그아웃 — P1
- 세션 쿠키 파기 후 공개 홈으로 이동

#### UC-AUTH-04 · 비인가 접근 차단 — P0
- **설명**: 비로그인 상태로 `/admin/**` 접근 시 `/admin/login`으로 리다이렉트
- **중요**: 이건 **UX 처리**이지 보안 경계가 아닙니다. 진짜 경계는 RLS입니다.
  미들웨어를 우회해도 DB가 데이터를 주지 않아야 합니다. (`02` 참조)

### 2.2 프로젝트 관리 (PRJ)

#### UC-PRJ-01 · 프로젝트 등록 — P0
- **액터**: Admin
- **입력 항목**

  | 항목 | 필수 | 비고 |
  |---|---|---|
  | 제목 (title) | ✅ | |
  | slug | ✅ | URL 식별자. 제목에서 자동 생성 + 수동 수정 허용 |
  | 한줄요약 (summary) | ✅ | 목록 카드 · OG description에 재사용 |
  | 상세설명 (description, 마크다운) | ⬜ | |
  | 시작일 / 종료일 | 시작일 ✅ | 종료일 `null` = 진행 중 |
  | 역할 (role) | ⬜ | 자유 텍스트 |
  | GitHub URL | ⬜ | |
  | 배포 URL | ⬜ | |
  | 상태 (draft/published) | ✅ | 기본값 `draft` |
  | 정렬 순서 | ✅ | 기본값 0 |

- **후조건**: 기본 `draft` 상태로 저장되어 방문자에게 보이지 않음
- **근거**: 기본값을 `draft`로 두는 것은 **안전한 기본값(secure by default)** 원칙입니다.
  실수로 미완성 글이 공개되는 사고를 구조적으로 막습니다.

#### UC-PRJ-02 · 프로젝트 수정 — P0
- 등록과 동일 항목. `slug` 변경은 허용하되 **경고 표시**
  (이미 공유된 링크가 깨지고 검색 색인이 초기화됨)
- 저장 성공 시 해당 프로젝트 상세 페이지 + 목록 페이지의 캐시를 무효화 (`03` 렌더링 전략 참조)

#### UC-PRJ-03 · 프로젝트 삭제 — P1
- **주 흐름**: 확인 다이얼로그 → 삭제 → 연결된 태그 매핑 및 이미지 레코드 연쇄 삭제
- **미결정 지점**: Storage의 실제 파일까지 지울지 여부 → §6 Q3
- **근거**: 백업이 없는 환경에서 삭제는 되돌릴 수 없습니다.
  그래서 P0이 아니라 P1입니다. MVP에서는 "비공개 전환"으로 대부분 대체 가능합니다.

#### UC-PRJ-04 · 공개 / 비공개 전환 — P0
- **설명**: `draft` ↔ `published` 토글
- **후조건**:
  - `published` → 목록·상세·사이트맵에 노출, 정적 페이지 재생성
  - `draft` → 즉시 목록에서 제거. 상세 URL 직접 접근 시 404
- **근거**: 아키텍처 원칙에 명시된 최우선 보안 요구사항의 실행 지점

#### UC-PRJ-05 · 관리자 프로젝트 목록 조회 — P0
- `draft` 포함 전체 목록. 상태 뱃지, 최근 수정일 표시

#### UC-PRJ-06 · 마크다운 미리보기 — P1
- **설명**: 작성 중 렌더링 결과 확인
- **근거**: 마크다운 입력의 결과를 저장 후에야 확인할 수 있으면 편집 루프가 너무 길어집니다.
  §0에서 관리자 편의성을 응답 속도보다 위에 둔 이유가 여기 적용됩니다.
- **주의**: 마크다운 → HTML 렌더링은 **XSS 표면**입니다. 입력자가 나 혼자라 위험도는 낮지만,
  살균(sanitize) 정책은 명시적으로 정해야 합니다. → §6 Q4

### 2.4 이미지 (IMG)

> 이 영역은 무료 티어 제약이 요구사항을 직접 규정하는 부분입니다.
> 상세 전략은 `04-free-tier-strategy.md`, 여기서는 사용자 관점 행동만 정의합니다.

#### UC-IMG-01 · 이미지 업로드 (다중) — P0
- **주 흐름**
  1. 파일 선택 또는 드래그앤드롭 (복수 선택 가능)
  2. **브라우저에서** 지정된 규격으로 리사이즈 및 WebP 변환
  3. 변환 결과와 원본을 각각 Storage에 업로드
  4. DB에 이미지 메타데이터(경로, 크기, variant 목록) 기록
- **제약**: 업로드 전 파일 크기 및 MIME 타입 검증
- **근거**: 변환을 클라이언트에서 하는 이유는 Vercel 이미지 변환 5,000회/월과
  서버리스 함수 실행 시간을 둘 다 아끼기 위함입니다 (확정된 결정사항)

#### UC-IMG-02 · 대표 이미지 지정 — P0
- 프로젝트당 정확히 0개 또는 1개. 다른 이미지를 지정하면 기존 대표는 자동 해제
- **근거**: 목록 카드와 OG 이미지가 이 값을 사용합니다. 없으면 목록이 텅 비어 보입니다

#### UC-IMG-03 · 이미지 순서 변경 / 삭제 — P1

#### UC-IMG-04 · 대체 텍스트(alt) 입력 — P1
- **근거**: 접근성 + SEO. 포트폴리오 사이트가 접근성을 어긴 채로 있으면 그 자체가 감점 요소입니다

### 2.5 공개 갤러리 (PUB)

#### UC-PUB-01 · 프로젝트 목록 조회 — P0
- **액터**: Visitor
- **표시**: 대표 이미지, 제목, 한줄요약, 태그 칩, 기간
- **정렬**: `display_order` 오름차순 → 시작일 내림차순
- **제약**: `published` 상태만 표시
- **렌더링**: 정적 (`03` 참조)

#### UC-PUB-02 · 태그 필터링 — P0
- **설명**: 태그 칩을 눌러 목록을 좁힘. 복수 선택 시 AND 조건
- **설계 제약**: 이 상호작용은 **클라이언트에서 처리**하고 서버 요청을 만들지 않습니다
- **근거**: 프로젝트가 10개 규모이므로 전체 데이터를 초기 페이로드에 담아도
  수십 KB에 불과합니다. 서버 필터링은 필터를 누를 때마다 서버리스 함수를 호출하게 되어
  §0의 1순위 기준(비용)에 어긋납니다. **작은 데이터셋이라는 사실이 아키텍처를 단순하게 만드는 사례**입니다
- **부가 조건**: 선택된 필터는 URL에 반영되어 공유·새로고침에도 보존되어야 함.
  단, 이 URL 반영이 페이지를 동적 렌더링으로 강등시키면 안 됨 (`03` 참조)

#### UC-PUB-03 · 프로젝트 상세 조회 — P0
- `/projects/{slug}`. 마크다운 렌더링, 스크린샷 갤러리, 외부 링크
- `draft` 프로젝트의 slug로 접근 시 **404** (403이 아님)
- **근거**: 403은 "그 리소스가 존재한다"는 정보를 흘립니다. 404가 정보 노출이 적습니다

#### UC-PUB-04 · 반응형 레이아웃 — P0
- **근거**: 채용 담당자가 모바일에서 링크를 여는 경우가 많습니다 (추측입니다 — 근거 데이터 없음).
  다만 모바일 미대응 포트폴리오의 감점 위험이 크므로 대응 비용 대비 타당합니다

#### UC-PUB-05 · 404 / 오류 페이지 — P1
- 갤러리로 복귀하는 경로 제공

### 2.6 시스템 (SYS)

#### UC-SYS-01 · DB Keep-alive — P0
- **설명**: 7일 무요청 시 자동 일시정지를 막기 위한 주기적 DB 접촉
- **근거**: 이건 기능이 아니라 **생존 조건**입니다. 방문이 산발적인 포트폴리오에서
  이게 없으면 정확히 "채용 담당자가 링크를 여는 순간"에 죽어 있을 확률이 높습니다.
  구현이 아무리 사소해도 P0입니다
- **상세**: `04-free-tier-strategy.md` §1

#### UC-SYS-02 · 데이터 백업 — P0
- **설명**: 스키마 + 데이터의 주기적 외부 저장
- **근거**: 무료 티어에는 자동 백업이 없습니다. 사고 시 복구 수단이 0입니다
- **상세**: `04-free-tier-strategy.md` §4

## 3. 비기능 요구사항

| ID | 항목 | 기준 | 검증 방법 |
|---|---|---|---|
| NFR-01 | 비용 | 월 $0 유지 | Vercel·Supabase 대시보드 월 1회 확인 |
| NFR-02 | 비공개 격리 | 익명 자격증명으로 `draft` 데이터 조회 불가 | 익명 키로 직접 REST 호출하여 확인 (스프린트 DoD) |
| NFR-03 | 공개 페이지 가용성 | DB 일시정지 상태에서도 공개 페이지 200 응답 | 정적 렌더링으로 구조적 보장 |
| NFR-04 | DB 미접속 무중단 기간 | 7일 미만 보장 | keep-alive 실행 로그 |
| NFR-05 | 초기 로딩 | 모바일 3G 기준 LCP 3초 이내 (목표치, 추측입니다) | Lighthouse |
| NFR-06 | 접근성 | 이미지 alt, 색 대비, 키보드 내비게이션 | 수동 점검 |
| NFR-07 | 타입 안정성 | DB 스키마에서 생성된 타입을 단일 소스로 사용 | 타입 생성물과 스키마 불일치 시 빌드 실패 |

> NFR-05를 "목표치, 추측입니다"로 표기한 이유: 실제 이미지 용량과 폰트 전략이 정해지기 전에는
> 달성 가능성을 단언할 수 없습니다. 스프린트 4에서 실측 후 확정합니다.

## 4. MVP에서 의도적으로 제외한 것

각 항목은 "안 함"이 아니라 **"지금 안 하는 이유가 명확함"** 을 기록한 것입니다.

| 제외 항목 | 이유 |
|---|---|
| **다중 사용자 / 역할 체계** | 운영자가 1명으로 확정. `profiles` 테이블과 역할 매핑을 만드는 순간 RLS 정책마다 조인이 붙습니다. 필요해지면 그때 JWT 클레임 검사 함수 하나만 교체하면 됩니다 — 확장 비용이 낮으므로 지금 만들 이유가 없습니다 |
| **회원가입 UI** | 계정은 1개이고 Supabase 대시보드에서 수동 생성합니다. 가입 경로가 존재하는 것 자체가 공격 표면입니다. Auth 설정에서 sign-up을 비활성화합니다 |
| **비밀번호 재설정 흐름** | 무료 티어 기본 SMTP는 발송량 제한이 크고 도달률이 불안정합니다(추측입니다). 계정 1개는 Supabase 대시보드에서 직접 복구할 수 있습니다 |
| **소프트 삭제 (`deleted_at`)** | `draft` 상태가 이미 "감추기" 요구를 충족합니다. 삭제와 비공개를 둘 다 두면 상태 조합이 늘고 RLS 정책이 복잡해집니다 |
| **감사 로그 / 변경 이력** | 작성자가 1명이라 "누가 바꿨나"라는 질문 자체가 성립하지 않습니다. 500MB DB에서 이력 테이블은 낭비입니다 |
| **댓글 · 방명록 · 좋아요** | 익명 쓰기 경로가 생기는 순간 스팸 대응, rate limiting, 신고 처리가 따라옵니다. 무료 티어 + 1인 운영에서 감당 범위를 벗어납니다 |
| **전문 검색 (full-text search)** | 10개 항목에서 검색창은 태그 필터보다 열등합니다. Postgres FTS 인덱스는 DB 용량도 씁니다 |
| **페이지네이션 / 무한 스크롤** | 10개 규모에서 불필요. 30개를 넘어서면 재검토 |
| **다국어 (i18n)** | 대상 독자가 정해지지 않았습니다. 라우팅 구조 전체에 영향을 주는 결정이므로 대상이 확정된 뒤에 도입해야 합니다 → §6 Q1 |
| **태그 병합 기능** | 태그 20개 미만에서는 수동 수정이 더 빠릅니다 |
| **이미지 크롭 · 편집 UI** | 업로드 전에 로컬 도구로 처리하는 편이 낫습니다. 브라우저 크롭 UI는 구현 비용이 이 기능의 가치보다 큽니다 |
| **조회수 카운터 컬럼** | `projects.view_count`를 두면 조회할 때마다 **쓰기**가 발생합니다. 그러면 (a) 공개 페이지를 정적으로 둘 수 없고, (b) 익명 롤에 UPDATE 권한을 줘야 하며, (c) 함수 호출이 조회수만큼 발생합니다. 세 가지 모두 §0 우선순위를 정면으로 위반합니다. 2단계에서 별도 이벤트 테이블 + 배치 집계로 갑니다 |
| **다크 모드** | 필수는 아니나 비용이 낮음. 스프린트 4에 여유가 있으면 포함 → §6 Q5 |
| **관리자 화면 반응형 최적화** | 관리는 데스크톱에서만 합니다. 깨지지만 않으면 충분합니다 |

## 6. 결정이 필요한 항목

- **Q1. 다국어를 나중에라도 할 가능성이 있습니까?**
  "없다"면 라우팅을 단순하게 갈 수 있습니다. "있을 수도 있다"면 지금 `projects` 텍스트 컬럼 구조를
  다르게 잡아야 합니다(나중에 바꾸면 마이그레이션 비용이 큼). 애매하면 "없다"로 가는 것을 권합니다.

- **Q2. 관리자 화면의 URL 경로를 추측하기 어렵게 만들까요?**
  `/admin` 그대로 두면 봇 스캔 대상이 됩니다. 실질 보안 효과는 없지만(RLS가 진짜 방어선),
  로그 노이즈와 불필요한 함수 호출이 줄어듭니다. 권고: `/admin` 유지 + `robots.txt` 차단 + 미들웨어 범위 한정.

- **Q3. 프로젝트 삭제 시 Storage의 실제 이미지 파일도 즉시 삭제할까요?**
  (a) 즉시 삭제 — 용량 회수는 확실하나 되돌릴 수 없음
  (b) DB 레코드만 삭제, 파일은 남김 — 고아 파일이 쌓임. 주기적 정리 작업 필요
  백업이 없다는 점을 감안하면 (b) + 분기별 수동 정리를 권합니다.

- **Q4. 마크다운에서 원시 HTML을 허용할까요?**
  허용하면 `<iframe>`으로 데모 영상 임베드 같은 게 가능해지지만 살균 정책이 필요합니다.
  권고: MVP는 원시 HTML **비허용**. 필요한 임베드는 별도 필드로 구조화.

- **Q5. 다크 모드를 스프린트 4 범위에 넣을까요?** (넣지 않으면 이후 색상 토큰 재작업이 조금 생깁니다)
