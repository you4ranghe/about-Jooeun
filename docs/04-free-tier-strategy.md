## 1. Supabase 7일 자동 일시정지 대응

### 1.1 문제의 성격

무료 프로젝트는 **7일간 DB 요청이 없으면 일시정지**됩니다.
포트폴리오는 방문이 산발적이므로 2주 넘게 아무도 안 오는 기간이 흔합니다.

그런데 이 아키텍처에서는 문제가 한 겹 더 있습니다.
**공개 페이지를 정적으로 만들었기 때문에, 방문자가 와도 DB 요청이 발생하지 않습니다.**
정적화는 비용 면에서 옳은 선택이지만, keep-alive 관점에서는 **문제를 악화시킵니다.**
방문자 트래픽에 의존할 수 없다는 뜻입니다.

### 1.2 일시정지가 실제로 일으키는 피해

| 영향 대상 | 결과 |
|---|---|
| 공개 갤러리 (정적 페이지) | ✅ 정상 — CDN이 서빙하므로 DB와 무관 |
| ISR 재검증 | ❌ 실패 → 오래된 캐시 계속 서빙 (그나마 다행) |
| 새 배포 (빌드) | ❌ **빌드 실패** — `generateStaticParams`가 DB 접속 |
| 관리 화면 | ❌ 전부 실패 |
| 복구 | 대시보드에서 수동 재개, 수 분 소요 |

**공개 페이지가 살아남는다는 점이 중요합니다.** 정적 렌더링 전략이
여기서 두 번째 배당금을 지급합니다. 그럼에도 keep-alive를 P0으로 두는 이유는,
"내가 모르는 사이에 DB가 잠들어 있고, 하필 그때 콘텐츠를 수정하려다 알게 되는" 상황이
운영 경험을 크게 망치기 때문입니다.

### 1.3 선택지 비교

| # | 방안 | 비용 | 신뢰성 | 부작용 | 평가 |
|---|---|---|---|---|---|
| A | **Vercel Cron** → `/api/keep-alive` | 무료 | 중 | Hobby는 **하루 1회 제한**, 실행 시각 부정확(추측입니다) · 함수 호출 소모(월 ~30회, 무시 가능) · **Vercel 배포가 깨지면 같이 죽음** | 보조로 적합 |
| B | **GitHub Actions cron** → Supabase REST 직접 호출 | 무료 | 중상 | **60일간 리포 활동이 없으면 스케줄이 자동 비활성화**됨 · 실행이 수십 분 지연될 수 있음 · Vercel과 독립적 | 주력 후보 |
| C | 외부 무료 cron 서비스 (cron-job.org 등) | 무료 | 상 | 서드파티 의존 · 계정 관리 포인트 추가 · 서비스 정책 변경 위험 | 3중화 시 고려 |
| D | 외부 업타임 모니터 (UptimeRobot 등) | 무료 | 상 | 5분 간격이면 월 8,600회 요청 → **Vercel 함수/대역폭을 불필요하게 소모** | ❌ 과함 |
| E | Supabase `pg_cron` (DB 내부 스케줄) | 무료 | ? | **DB 내부 작업이 "요청"으로 집계되는지 불확실**(추측입니다). 게다가 이미 일시정지된 뒤엔 실행되지 않아 자가복구 불가 | ❌ 단독 사용 부적합 |

### 1.4 권고안: B(주력) + A(보조) 이중화

```
[GitHub Actions]  월/목 09:00 UTC
      │
      ├─(1) Supabase REST 직접 호출  ──→ Supabase Postgres
      │     GET /rest/v1/tags?select=id&limit=1              ★ 진짜 DB 요청
      │
      └─(2) pg_dump 백업 → private repo 커밋                  ★ §4와 통합
                    │
                    └─→ 리포 활동 발생 → 60일 비활성화 문제 자동 해소

[Vercel Cron]     매일 03:00 UTC
      └─→ GET /api/keep-alive  ──→ 서버에서 가벼운 DB 쿼리 1건
```

**이 조합을 고르는 이유**

1. **주력이 Vercel과 독립적이다** — GitHub Actions는 Supabase REST를 직접 호출합니다.
   Vercel 배포가 깨져 있어도, 앱에 버그가 있어도 keep-alive는 돕니다.
   장애 상관관계를 끊는 것이 이중화의 핵심입니다.
2. **60일 비활성화 문제가 저절로 풀린다** — GitHub Actions의 스케줄은 리포 활동이
   60일간 없으면 비활성화됩니다. 그런데 이 워크플로가 **백업 파일을 커밋**하므로
   매 실행이 곧 리포 활동입니다. 자기 자신을 살려두는 구조입니다.
   > **단, 봇 커밋(`github-actions[bot]`)이 "리포 활동"으로 집계되는지는 확실하지 않습니다 — 추측입니다.**
   > 이 불확실성 때문에 A(Vercel Cron)를 보조로 함께 둡니다. 이중화의 두 번째 이유입니다.
3. **주 2회 = 최대 공백 4일** — 7일 한도에 3일의 여유가 있습니다.
   한 번 실패해도 다음 실행까지 버팁니다. Vercel Cron이 매일 도는 것까지 합치면
   실질적으로 매일 접촉합니다.
4. **백업과 통합되어 관리 포인트가 늘지 않는다** — 워크플로 파일 하나입니다.

**주 2회로 잡은 근거**: 매일 돌려도 비용은 같지만, GitHub Actions 실행 로그가 쌓이고
백업 커밋이 매일 생기면 리포 히스토리가 지저분해집니다. 주 2회면 7일 한도 대비
2배 이상의 안전 여유가 있으면서 히스토리가 관리 가능한 수준입니다.

### 1.5 `/api/keep-alive` 설계

- **인증**: `KEEP_ALIVE_SECRET`을 헤더로 검사. 공개 엔드포인트로 두면 누구나 호출해
  함수 호출을 소모시킬 수 있습니다
- **동작**: 가장 가벼운 쿼리 1건. `tags`에서 `id` 1행 조회 정도.
  **쓰기를 하면 안 됩니다** — 쓰기는 데이터를 오염시키고 되돌릴 방법이 없습니다
- **반환**: 상태와 타임스탬프. 실패 시 5xx (스케줄러가 실패를 감지할 수 있도록)
- **캐시 금지**: `dynamic = 'force-dynamic'`. 캐시되면 DB에 닿지 않아 목적이 무산됩니다.
  **이걸 빠뜨리면 keep-alive가 조용히 무의미해집니다** — 가장 실수하기 쉬운 지점입니다

### 1.6 실패 감지

keep-alive가 조용히 멈추는 것이 최악입니다. 감지 수단을 둡니다.

- **GitHub Actions**: 워크플로 실패 시 기본적으로 이메일 알림이 옵니다.
  별도 설정 없이 얻는 감시입니다
- **월 1회 수동 확인**: Supabase 대시보드에서 프로젝트 상태와
  마지막 활동 시각을 확인합니다. `05` 스프린트 5의 운영 체크리스트에 포함

### 1.7 그래도 일시정지되었을 때의 복구 절차

1. Supabase 대시보드에서 프로젝트 재개 (수 분 소요)
2. keep-alive 워크플로의 최근 실행 로그 확인 → 왜 멈췄는지 파악
3. 데이터 무결성 확인 (일시정지 자체로는 데이터가 사라지지 않습니다)
4. 재개 후 Vercel에서 재배포 (빌드가 실패한 상태로 남아 있을 수 있음)

> **90일 이상 일시정지 상태가 지속되면 프로젝트가 삭제될 수 있다고 알고 있습니다 — 추측입니다.**
> 정확한 정책은 확인이 필요하지만, 어느 쪽이든 §4의 백업이 최종 방어선입니다.

## 2. 이미지 전략

### 2.1 확정된 방향

**업로드 시점에 브라우저에서 사전 변환 → Supabase public 버킷 → CDN 직접 서빙**

이 결정으로 **Vercel 이미지 변환 사용량이 0이 됩니다.** 5,000회/월 한도를
아예 건드리지 않으므로, 한도 관리 대상에서 항목 하나가 통째로 사라집니다.

### 2.2 변환 규격

| variant | 폭 | 포맷 | 품질 | 용도 | 예상 용량 |
|---|---|---|---|---|---|
| `thumb` | 400px | WebP | 75 | 목록 카드 | ~25 KB |
| `md` | 800px | WebP | 80 | 상세 갤러리 | ~70 KB |
| `lg` | 1600px | WebP | 80 | 상세 대표 · 라이트박스 | ~200 KB |
| (원본) | 원본 | 원본 | — | private 보관 | ~2.5 MB |
| `blur` | ~20px | WebP → base64 | 40 | LQIP (DB에 저장) | ~0.5 KB |

**용량 수치는 1600×1000 스크린샷 기준 추정치입니다 — 실측 아님.**
스프린트 3에서 실제 이미지로 검증하고 이 표를 갱신합니다.

**3단계로 나눈 근거**

- 2단계(thumb/lg)면 목록에서 25KB, 상세에서 200KB로 점프합니다.
  상세 갤러리의 여러 장을 전부 lg로 받으면 낭비가 큽니다
- 4단계 이상은 저장 용량과 업로드 시간만 늘고 실익이 적습니다
- **AVIF를 쓰지 않는 이유**: WebP보다 20~30% 작지만(추측입니다),
  브라우저 Canvas의 AVIF 인코딩 지원이 불균일하고 인코딩이 느립니다.
  사전 변환 방식에서는 브라우저 인코더 성능이 직접적인 UX 비용입니다

### 2.3 원본을 보관하는 이유

private 버킷에 원본을 남깁니다. 장당 2.5MB × 40장 ≈ 100MB로 1GB의 10%입니다.

- 나중에 규격을 바꾸거나(AVIF 전환 등) 품질을 다시 뽑으려면 원본이 필요합니다
- 원본 없이 variant만 남기면 **되돌릴 수 없습니다**. 재생성이 불가능한 손실입니다
- 용량 여유가 충분한데 되돌릴 수 없는 선택을 할 이유가 없습니다

### 2.4 Vercel 이미지 최적화와의 역할 분담

| 역할 | 담당 |
|---|---|
| 리사이즈 · 포맷 변환 | **브라우저 (업로드 시 1회)** |
| 저장 · CDN 배포 | **Supabase Storage (public 버킷)** |
| 반응형 `srcset` | **애플리케이션이 variant 경로로 직접 구성** |
| lazy loading · 레이아웃 시프트 방지 | `next/image` (`unoptimized` 모드) |
| 런타임 이미지 변환 | **사용 안 함** |

`next/image`를 완전히 버리지 않고 `unoptimized`로 쓰는 이유:
`width`/`height` 기반 종횡비 예약과 lazy loading은 여전히 유용하고,
이 기능들은 변환 한도를 소모하지 않습니다. (`03` §10 Q4)

### 2.5 캐시 정책

- 업로드 시 `cacheControl: 'public, max-age=31536000, immutable'`
- 경로가 UUID 기반 불변이므로 immutable이 안전합니다
- **효과**: 재방문·재크롤 시 CDN이 응답하고 Supabase origin에 요청이 가지 않습니다.
  egress 5GB 한도 소진을 크게 늦춥니다
  > **Supabase 무료 티어에서 CDN 캐시 히트분이 egress에 집계되는지는 확실하지 않습니다 — 추측입니다.**
  > §5의 추산은 **캐시 이득을 전혀 계산하지 않은 보수적 수치**로 잡았습니다.
  > 캐시가 집계에서 빠진다면 실제 사용량은 추산보다 훨씬 낮을 것입니다.

### 2.6 업로드 시 검증

| 항목 | 기준 | 이유 |
|---|---|---|
| 파일 크기 | 10MB 이하 | 브라우저 변환 성능 · 스토리지 보호 |
| MIME 타입 | jpeg / png / webp | |
| 해상도 | 4000px 이하 | Canvas 메모리 한계 |
| 프로젝트당 장수 | 10장 이하 | 용량 예측 가능성 유지 |

## 3. 대역폭 및 함수 호출 절약 설계

절약 수단을 효과 순으로 정리합니다. **대부분은 이미 아키텍처에 반영되어 있고,
여기서는 "왜 그게 비용 설계였는지"를 명시합니다.**

| # | 수단 | 절약 대상 | 효과 |
|---|---|---|---|
| 1 | **공개 페이지 정적 렌더링** | Vercel 함수 호출 | 방문 트래픽의 함수 호출을 **0으로** 만듦. 단일 최대 효과 |
| 2 | **미들웨어 matcher를 `/admin/*`로 한정** | Vercel 함수(Edge) 호출 | 공개 트래픽이 미들웨어를 전혀 거치지 않음. 기본 설정 대비 수천 배 차이 |
| 3 | **이미지를 Supabase CDN에서 직접 서빙** | Vercel 대역폭 · 변환 | 전체 트래픽의 80~90%를 차지하는 이미지가 Vercel을 우회 |
| 4 | **이미지 사전 변환** | Vercel 이미지 변환 | 5,000회 한도 사용량 0 |
| 5 | **`immutable` 캐시 헤더** | Supabase egress | 재방문 시 origin 요청 없음 |
| 6 | **태그 필터를 클라이언트에서 처리** | Vercel 함수 호출 | 필터 조작이 서버 요청을 만들지 않음 |
| 7 | **on-demand ISR (시간 기반 최소화)** | Vercel 함수 호출 | 저장할 때만 재생성. 짧은 TTL로 주기 재생성하지 않음 |
| 8 | **Tailwind + 서버 컴포넌트 위주** | Vercel 대역폭 | JS/CSS 번들 최소화 |
| 9 | **마크다운을 서버에서 HTML로 변환** | Vercel 대역폭 | 파서가 클라이언트 번들에 들어가지 않음 (`03` Q1) |
| 10 | **`robots.txt`로 관리 경로 차단** | 함수 호출 | 크롤러가 SSR 경로를 긁지 않음 |

### 3.1 봇 트래픽 — 추산에서 가장 큰 불확실성

추산은 사람 방문자 기준입니다. 실제로는 검색 크롤러, SNS 미리보기 봇,
AI 학습 크롤러가 상당한 비중을 차지할 수 있습니다.
**개인 사이트에서 봇이 트래픽의 절반 이상인 경우가 드물지 않습니다 — 추측입니다.**

- 공개 페이지가 정적이므로 봇이 와도 **함수 호출은 0**입니다. 대역폭만 씁니다
- 대역폭은 100GB로 여유가 크므로 실질 위험은 낮습니다
- 다만 **이미지를 대량으로 긁는 봇**은 Supabase egress에 영향을 줄 수 있습니다
- **대응**: `robots.txt`에 관리 경로 차단을 명시하고,
  월간 사용량 확인 시 이상 급증이 있으면 그때 특정 User-Agent를 차단합니다.
  **선제적으로 차단하지는 않습니다** — 검색 노출은 포트폴리오의 목적 중 하나이므로,
  실제 문제가 관측되기 전에 크롤러를 막는 것은 손해입니다

## 4. 백업 전략

### 4.1 위험 규정

무료 티어에는 **자동 백업이 없습니다.** 다음 상황에서 데이터가 영구 소실됩니다.

| 시나리오 | 확률 | 피해 |
|---|---|---|
| 실수로 DELETE / 잘못된 마이그레이션 | 중 | 전체 또는 일부 |
| `ON DELETE CASCADE` 연쇄 삭제 사고 | 중 | 연결 데이터 |
| 계정 접근 상실 | 낮음 | 전체 |
| 장기 일시정지 후 프로젝트 삭제 | 낮음 | 전체 |
| Supabase 측 장애 | 매우 낮음 | 전체 |

**확률로 보면 1~2번(내 실수)이 압도적입니다.**
그래서 백업 설계의 초점은 "Supabase가 죽을 때"가 아니라
**"내가 실수했을 때 되돌릴 수 있는가"** 여야 합니다.

### 4.2 대상별 전략

| 대상 | 방법 | 주기 | 저장 위치 |
|---|---|---|---|
| **DB 스키마** | 마이그레이션 파일 | 변경 시마다 | Git (이미 확보됨) |
| **DB 데이터** | `pg_dump` | 주 2회 (keep-alive와 통합) | **private GitHub repo** |
| **Storage 원본** | 로컬 원본 폴더 | 업로드 시 | 로컬 디스크 |
| **Storage variant** | 원본에서 재생성 가능 | — | 백업 불필요 |
| **환경 변수 / 시크릿** | 비밀번호 관리자에 수기 보관 | 변경 시 | 로컬 |

**Storage를 git에 넣지 않는 이유**: 원본 100MB를 git에 커밋하면 히스토리가 급격히 커지고
GitHub 리포 권장 용량을 위협합니다. 그런데 **원본은 애초에 내 컴퓨터에서 올린 것**이므로
이미 로컬에 있습니다. 별도 백업을 만드는 대신 **로컬 원본 폴더를 원천으로 취급**하고
지우지 않는 운영 규칙을 두는 것이 비용 대비 효과가 좋습니다.

**variant를 백업하지 않는 이유**: 원본이 있으면 언제든 다시 만들 수 있는 파생물입니다.
파생물을 백업하는 것은 낭비입니다.

### 4.3 통합 워크플로 (개념)

```
GitHub Actions (월/목 09:00 UTC)
  │
  ├─ 1. Supabase REST에 GET 1건            → keep-alive (§1)
  ├─ 2. pg_dump 실행 (데이터 + 스키마)      → backup/dump.sql
  ├─ 3. 변경이 있으면 커밋 & 푸시            → 백업 저장 + 리포 활동 발생
  └─ 4. 실패 시 이메일 알림 (기본 동작)      → 감시
```

**설계 세부**

- **덤프 파일명을 고정합니다** (`backup/dump.sql`). 날짜별 파일을 쌓으면 리포가 계속 커집니다.
  **git 히스토리 자체가 세대 관리 역할을 합니다** — 과거 시점 복원은 커밋을 되짚으면 됩니다.
  이게 git을 백업 저장소로 쓰는 가장 큰 이점입니다
- 덤프 예상 크기는 **1MB 미만**입니다(텍스트만 저장하므로). 주 2회 커밋해도 부담 없습니다
- **변경이 없으면 커밋하지 않습니다** — 다만 그러면 리포 활동이 발생하지 않아
  §1.4의 60일 문제가 되살아납니다. **대응: 덤프에 실행 타임스탬프를 포함시켜
  매번 최소 1줄이 바뀌게 합니다.** 조금 지저분하지만 목적이 분명합니다
- **private 리포에 저장합니다.** 덤프에는 아직 공개하지 않은 `draft` 콘텐츠가 들어 있습니다

**예상되는 기술적 난관 (미리 적어둠)**

- **연결 방식**: Supabase의 직접 연결(direct connection)이 IPv6 전용인 경우가 있어,
  GitHub Actions 러너(IPv4)에서 접속이 실패할 수 있습니다.
  이 경우 **connection pooler 엔드포인트**를 사용해야 합니다. — **추측입니다.**
  스프린트 5에서 실제로 부딪혀 확인할 지점입니다
- **`pg_dump` 버전**: 러너의 클라이언트 버전이 서버보다 낮으면 거부됩니다.
  Postgres 클라이언트를 명시적 버전으로 설치해야 합니다
- **필요 시크릿**: DB 연결 문자열(비밀번호 포함). GitHub Secrets에 보관

### 4.4 복구 시나리오

| 상황 | 절차 |
|---|---|
| 특정 프로젝트를 실수로 삭제 | 최신 덤프에서 해당 행만 추출해 수동 INSERT |
| 잘못된 마이그레이션 적용 | 로컬에서 덤프를 복원해 검증 → 수정 마이그레이션 작성 → 운영 반영 |
| DB 전체 소실 | 새 Supabase 프로젝트 생성 → 마이그레이션 전체 적용 → 덤프 데이터 복원 → 환경변수 교체 → 재배포 |
| Storage 소실 | 로컬 원본 폴더에서 재업로드 (variant는 자동 재생성) |

### 4.5 **복구 리허설 (필수)**

**테스트하지 않은 백업은 백업이 아닙니다.**
스프린트 5의 DoD에 다음을 포함합니다.

1. 최신 덤프를 받아 **로컬 Supabase에 실제로 복원**한다
2. 프로젝트 수, 태그 연결, 이미지 메타데이터가 온전한지 확인한다
3. 소요 시간과 막힌 지점을 기록한다

> 이 리허설을 한 번 해두면, 실제 사고가 났을 때 "복구 방법을 모르는 상태에서
> 당황하는" 최악의 시나리오를 피할 수 있습니다.
> 로컬 Supabase 환경을 갖춘 것(`03` §8.5)이 여기서 두 번째 배당금을 지급합니다.

### 4.6 운영 규칙

- **운영 마이그레이션 적용 전에는 반드시 백업 워크플로를 수동 실행합니다.**
  주 2회 자동 실행 사이에 큰 변경을 넣으면 최대 3~4일치가 날아갈 수 있습니다
- 로컬 이미지 원본 폴더를 지우지 않습니다

## 5. 한도별 소진 추산

### 5.1 추산 전제

| 항목 | 값 | 근거 |
|---|---|---|
| 프로젝트 수 | 10개 | 합의된 가정 |
| 이미지 총 장수 | 40장 (프로젝트당 4장) | 합의된 가정 |
| 월 방문자 | 500명 | 합의된 가정 |
| 방문자당 페이지뷰 | 3 | 목록 1 + 상세 2 (**추측입니다**) |
| 월 페이지뷰 | 1,500 | 500 × 3 |
| 목록 페이지 이미지 | 10 × thumb(25KB) = 250KB | §2.2 |
| 상세 페이지 이미지 | lg 1장 + md 3장 ≈ 410KB | lazy loading으로 실제는 더 적음 |
| 페이지뷰당 평균 이미지 | ~360 KB | 목록/상세 혼합 |
| 페이지뷰당 HTML+JS+CSS | ~200 KB | 초회 기준 (**추측입니다**) |
| **CDN 캐시 이득** | **0으로 가정** | 보수적 추산 (§2.5) |

### 5.2 항목별 추산

| 한도 | 월 예상 사용 | 비율 | 소진까지 |
|---|---|---|---|
| **Supabase DB 500MB** | < 1 MB | < 0.2% | 사실상 도달 불가 |
| **Supabase Storage 1GB** | 112 MB (누적) | 11% | **프로젝트 약 85개** 분량 |
| **Supabase egress 5GB/월** | ~540 MB | ~11% | **월 12,500 PV** (현재의 8배) |
| **Vercel 대역폭 100GB/월** | ~300 MB | 0.3% | **월 40만 PV** — 도달 불가 |
| **Vercel 함수 호출 1M/월** | ~1,500회 | 0.15% | 도달 불가 |
| **Vercel 이미지 변환 5,000/월** | **0회** | 0% | 미사용 |

**계산 근거**

- Storage: 원본 40×2.5MB = 100MB, variant 40×295KB ≈ 12MB → **112MB**
- Supabase egress: 1,500 PV × 360KB ≈ **540MB**
- Vercel 대역폭: 1,500 PV × 200KB ≈ **300MB**
- 함수 호출: 관리 작업 ~1,000 + ISR 재생성 ~50 + keep-alive ~40 + 여유 ≈ **1,500**

### 5.3 임계점 (언제 위험해지는가)

| 조건 | 처음 걸리는 한도 |
|---|---|
| 월 페이지뷰 **12,500** 돌파 | Supabase egress 5GB |
| 프로젝트 **85개** 돌파 | Storage 1GB |
| 월 페이지뷰 40만 돌파 | Vercel 대역폭 (비현실적) |

**즉, 이 설계에서 가장 먼저 닿는 한도는 Supabase egress이며, 그것도 현재 가정의 8배
트래픽이 필요합니다.** 개인 포트폴리오가 월 12,500 페이지뷰에 도달한다면
그건 축하할 일이지 문제가 아닙니다.

### 5.4 초과 시 대응 (우선순위 순)

**Supabase egress가 위험해지면**

1. 캐시 헤더가 제대로 적용되고 있는지 확인 (가장 흔한 원인)
2. 이미지 품질 파라미터를 낮춰 재변환 (원본이 있으므로 가능 — §2.3의 이유)
3. thumb 폭을 400 → 320px로 축소
4. 이미지를 다른 무료 CDN으로 분리 (최후 수단, 구조 변경 필요)

**Storage가 위험해지면**

1. 오래된 프로젝트의 **원본**을 로컬로 내리고 Storage에서 삭제 (variant는 유지)
2. 프로젝트당 이미지 장수 제한을 강화

**Vercel 대역폭 / 함수 호출이 위험해지면**

1. 어느 경로가 소모하는지 대시보드에서 확인
2. 정적이어야 할 페이지가 동적으로 렌더링되고 있지는 않은지 점검
   — **가장 가능성 높은 원인**입니다. `searchParams` 사용, 캐시되지 않는 `fetch`,
   미들웨어 matcher 확대 등이 조용히 이 사고를 냅니다 (`03` §3.1)

### 5.5 모니터링

- **월 1회** Vercel · Supabase 대시보드에서 사용량 확인 (`05` 스프린트 5 체크리스트)
- Vercel 사용량 알림을 활성화 (75% 도달 시 통지 — 정확한 임계값은 확인 필요, **추측입니다**)
- **초과 시 과금이 아니라 서비스 중단**이므로, 알림을 받는 것 자체가 중요합니다

## 8. 결정이 필요한 항목

- **Q1. keep-alive 주기를 주 2회로 할까요, 매일로 할까요?**
  주 2회는 최대 공백 4일(7일 대비 여유 3일)입니다. 매일이면 여유가 크지만
  백업 커밋이 매일 쌓입니다. 권고: **주 2회 + Vercel Cron 매일 보조.**

- **Q2. 백업 저장소를 별도 private 리포로 분리할까요, 소스 리포 안에 둘까요?**
  같은 리포에 두면 관리가 단순하지만, 소스 리포를 나중에 **공개로 전환**할 때
  `draft` 콘텐츠가 그대로 노출됩니다. 포트폴리오 프로젝트는 소스를 공개하고 싶어질
  가능성이 높으므로, **별도 private 리포를 권합니다.**

- **Q3. 프로젝트 이미지 원본의 로컬 보관 위치를 정해두시겠습니까?**
  "어딘가에 있겠지"는 백업 전략이 아닙니다. 고정된 폴더 경로를 정하고
  `05`의 운영 체크리스트에 명시하는 것을 권합니다.

- **Q4. 이 포트폴리오에 프리랜스 문의 / 단가 관련 내용을 넣을 계획이 있습니까?** (§7)
  "없다"면 Hobby 플랜 리스크를 논의에서 제외할 수 있습니다.

- **Q5. Vercel Cron(보조 keep-alive)을 생략할까요?**
  GitHub Actions 하나로도 7일 한도는 충족합니다. 이중화를 권하는 이유는
  §1.4의 60일 비활성화 불확실성 때문입니다.
  단순함을 우선한다면 GitHub Actions 단독 + 월 1회 수동 확인도 합리적 선택입니다.
