# 09. 이력서·소개를 화면에서 고치기

> **상태: 확정 (2026-07-31).**
>
> | | 정한 것 |
> | --- | --- |
> | Q1 예시 12개 | **DB 는 비우고, 지금 값은 편집 폼의 입력 예시(placeholder)로** 옮깁니다 |
> | Q2 소개 | **같이 옮깁니다** |
> | Q3 편집 화면 | **목록 + 폼.** 미리보기는 만들지 않습니다 |
>
> Q1 은 제안받은 절충안입니다. 지우자니 빈 폼 앞에서 무엇을 쓸지 막막하고,
> 넣자니 가짜가 DB 로 옮겨 갑니다. **폼의 회색 예시 글자**로 두면
> 쓸 때는 길잡이가 되고 공개되는 곳에는 한 글자도 나가지 않습니다.

소스 파일을 열어 하드코딩하던 이력서와 소개를 **관리자가 화면에서 고치도록** 옮깁니다.
캘린더(docs/06 P4)에서 이미 세운 Supabase + Auth + RLS 를 그대로 씁니다.

## 1. 이번에 옮기는 것과 옮기지 않는 것

| | 지금 | 뒤 |
| --- | --- | --- |
| **이력서 12항목** | `content/resume.ts` 하드코딩 | **DB + 관리자 편집** |
| **소개**(이름·직함·연락처) | 컴포넌트 안 문자열 | **DB + 관리자 편집** |
| 프로젝트 상세 | `content/projects.ts` | **그대로 둡니다** |

### 프로젝트를 옮기지 않는 이유

프로젝트 하나가 **필드 예순 개 남짓**입니다. 테마 13개, 히어로와 증거는 종류마다
모양이 다른 유니온, 거기에 결정·만든 것·수치·한계 배열. 이걸 위한 폼은
포트폴리오가 아니라 CMS 한 채입니다.

그리고 저장소를 붙일 때 오래 걸리는 일은 입력이 아니라 **README 를 읽고
버린 선택지를 찾아 문장으로 만드는 일**입니다. 폼이 있어도 그 시간은 그대로입니다.

## 2. 지켜야 할 선 — 정적 렌더링

지금 `/` · `/projects` · `/projects/[slug]` 는 **정적**입니다.
함수 호출 0, DB 가 잠들어 있어도 방문자에게는 멀쩡합니다.
무료 Supabase 는 7일 요청이 없으면 일시정지되는데, 그때도 사이트가 도는 것이
이 구조의 핵심입니다(docs/04).

**이력서를 요청마다 DB 에서 읽으면 그 장점이 통째로 사라집니다.**
게다가 이력서는 `(site)/layout.tsx` 가 읽어 셸에 내려 줍니다 — 그 아래 **모든 라우트**가
동적으로 강등됩니다. 채용 담당자가 링크를 열었는데 DB 가 자고 있어 이력서가 비어 있는 것,
이게 이 사이트에서 낼 수 있는 최악의 실패입니다.

### 그래서 태그 캐시 + 저장 시 갱신

이미 `/api/weather` 에서 쓰고 있는 방법입니다. Supabase 클라이언트 대신
**REST 엔드포인트를 `fetch` 로** 부르고 Next 데이터 캐시에 태그를 붙입니다.

```
읽기   fetch(`${SUPABASE_URL}/rest/v1/resume_items?...`,
             { next: { tags: ["resume"] } })     ← 무기한 캐시
쓰기   서버 액션에서 저장 → revalidateTag("resume")  ← 그때만 다시 굽습니다
```

평소에는 정적으로 서빙되고, **관리자가 고칠 때만** 페이지가 새로 구워집니다.
방문자 요청으로는 DB 에 한 번도 가지 않습니다.

> **DB 가 죽어 있으면?** 이미 구워 둔 정적 HTML 이 계속 나갑니다.
> 완전히 새로 빌드하는 순간에만 문제가 되고, 그때는 빈 목록으로 두고
> "준비 중" 을 그립니다. 빌드를 깨뜨리지 않습니다(docs/03 §3.1 과 같은 원칙).

## 3. 표 두 개

### `resume_items`

| 칼럼 | 타입 | 비고 |
| --- | --- | --- |
| `id` | text PK | `intro` · `career-a` 같은 식별자 |
| `sort` | int | 화면 순서 |
| `art` | text | 방에 놓을 그림 키 (`ArtKey`) |
| `category` `short` `title` `lead` `tip` | text | 카드 머리말 |
| `rows` `chips` `body` `links` | jsonb | 배열 넷 |
| `published` | boolean | 안 보이게 두고 쓰던 중일 때 |
| `updated_at` | timestamptz | |

**왜 jsonb 인가.** `rows` · `chips` · `body` · `links` 는 **따로 조회되는 일이 없습니다.**
언제나 항목 하나와 통째로 읽고 통째로 씁니다. 표 넷으로 쪼개면 조회는 조인 네 번,
저장은 지우고 다시 넣기가 되는데 얻는 것이 없습니다.
따로 검색하거나 집계할 일이 생기면 그때 쪼갭니다.

### `profile` — 한 줄짜리

| 칼럼 | 비고 |
| --- | --- |
| `id` | `smallint primary key check (id = 1)` — 한 행만 존재 |
| `name` `role` `email` `github` `intro` | 벽에 붙은 이름표와 폰의 소개 앱이 씁니다 |

## 4. 권한 — 캘린더와 **반대**입니다

캘린더는 `anon` 에게서 권한을 **완전히 걷어냈습니다**(비공개 일정).
이력서는 그 반대입니다. **읽기는 누구나, 쓰기는 관리자만.**

```
읽기  anon  SELECT  where published = true   ← 이력서는 공개 콘텐츠입니다
쓰기  관리자만 (app_metadata.role = 'admin')  ← 캘린더와 같은 판정
```

> 이력서를 anon 이 읽는 것은 새는 게 아니라 **하라고 만든 일**입니다.
> 다만 `published = false` 인 초안은 읽히면 안 되므로 정책에 조건을 겁니다.

## 5. 어디서 고치나

**`/admin/resume`** — 미들웨어가 이미 `/admin/:path*` 를 막고 있습니다.

방 안에서 인라인으로 고치는 방법도 생각했지만 접었습니다.
캘린더는 **월 격자 자체가 편집 화면**이라 제자리 편집이 자연스럽습니다.
이력서 한 항목은 표·칩·본문 여러 단락이 붙은 문서라, 벽에 걸린 288px 종이 안에서
고치는 것은 화면을 학대하는 일입니다.

대신 **들어가는 문은 화면 안에 둡니다.**
관리자로 보고 있으면 이력서 목록 위에 `편집` 이 뜨고, 누르면 폼으로 갑니다.
방문자에게는 그 버튼이 아예 없습니다.

## 6. 정해야 할 것 세 가지

### Q1. 지금 있는 예시 12개를 어떻게 할까

| | 안 A — 빈 상태로 시작 | 안 B — 예시를 그대로 넣고 고치기 |
| --- | --- | --- |
| 사이트 | 채울 때까지 "준비 중" | 지금과 같아 보임 |
| 정직함 | **가짜가 완전히 사라짐** | 가짜가 DB 로 옮겨 감 |
| 실수 위험 | 없음 | 안 고친 항목이 진짜인 척 남음 |

권고는 **A** 입니다. 지금 12개는 제가 지어낸 값이고, 그것 때문에 검색 색인이 잠겨
있습니다. DB 로 옮겨 놓으면 "언젠가 고치지" 가 되고, 하나 빠뜨리면 그게 실명 도메인에
남습니다. 빈 상태에서 하나씩 채우는 편이 빠르고 안전합니다.

### Q2. 소개도 같이 옮길까

이름·직함·이메일·GitHub 은 지금 **컴포넌트 안 문자열**입니다(벽 이름표, 폰 소개 앱).
표 하나에 행 하나라 비용이 거의 없고, 옮기면 연락처를 화면에서 고칠 수 있습니다.
권고는 **같이 옮기기**.

### Q3. 편집 화면을 어디까지 만들까

| | 안 A — 목록 + 폼 (권장) | 안 B — 여기에 미리보기까지 |
| --- | --- | --- |
| | 순서 바꾸기 · 감추기 · 항목 추가/삭제 | 고치면서 카드 모양을 옆에서 봄 |
| 크기 | 보통 | 큼 |

권고는 **A** 입니다. 미리보기는 방에서 그 카드를 열어 보면 그만이고,
편집 화면을 두 배로 키울 값어치가 없습니다.
