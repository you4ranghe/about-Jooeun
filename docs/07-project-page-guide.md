# 07. 프로젝트 상세페이지 디자인 가이드

`/projects/[slug]` 한 장을 어떻게 만들지 정해 둔 문서입니다.
2026-07-30 에 시안 세 개 중 **A · 결정 대장**(`design/06-detail-ledger.html`)을 골랐고,
그것을 12개 저장소에 쓸 수 있는 **틀**로 바꾸는 것이 이 문서의 목적입니다.

---

## 1. 왜 가이드가 먼저인가

시안 하나를 그대로 12번 복제하면 두 가지 중 하나가 됩니다.

| 안 하면 생기는 일             | 결과                                                     |
| ----------------------------- | -------------------------------------------------------- |
| 프로젝트마다 자유롭게 만들기  | 12개가 제각각이 되어 한 사람의 포트폴리오로 안 읽힘      |
| 시안을 그대로 복제하기        | 두 번째 페이지부터 안 읽힘. 다 본 것 같으니까            |

**둘 다 피하려면 무엇이 고정이고 무엇이 변하는지를 미리 못 박아야 합니다.**
그러면 저장소를 새로 받을 때 하는 일이 "새로 디자인하기"가 아니라 **"고르기"** 가 됩니다.

---

## 2. 원칙 — 뼈대는 하나, 성격은 두 자리에서 만든다

> **2026-07-30 정정.** 처음에는 "바탕은 절대 바꾸지 않는다"로 적었습니다.
> 그대로 두 개를 만들어 보니 **두 페이지가 사실상 같았습니다.** 달라진 건
> 강조색 하나와 히어로 블록 하나뿐이었고, 둘 다 배포된 웹이라 증거까지 같았습니다.
> 경계를 잘못 그은 것이라 아래처럼 옮깁니다. 옛 규칙은 §5 끝에 남겨 둡니다.

```
┌─ 고정 ─────────────────────────────────────────┐
│  정보 순서 (히어로 → 증거 → 결정 → 만든 것 →   │
│             배운 것 / 아직 못 한 것)            │
│  결정 대장이라는 장치 (버린 길 / 택한 길)       │
│  최소 글씨 크기 · 접근성 · reduced-motion       │
└────────────────────────────────────────────────┘
        ↑ 여기가 같아서 한 사람의 포트폴리오로 읽힙니다

┌─ 변함 ─────────────────────────────────────────┐
│  ① 그 사이트의 팔레트 **한 벌 전체**            │
│     바탕 · 카드 · 글자 · 선 · 강조 · 밝기 방향  │
│  ② 표제 폰트 (고딕 / 명조) · 모서리 반경        │
│  ③ 히어로 장치   — 무엇으로 첫 문장을 대신할까 │
│  ④ 증거 블록     — 무엇으로 "진짜"를 보여줄까  │
│  ⑤ 수치 다섯 개  — 이 프로젝트에서 자랑할 숫자 │
└────────────────────────────────────────────────┘
        ↑ 여기가 달라서 페이지마다 다른 사이트처럼 보입니다
```

**상세페이지는 그 프로젝트 사이트의 옷을 입습니다.**
윷놀이는 남색 바탕에 청록, 인터페이퍼는 회백 종이에 흰 카드와 명조입니다.
두 페이지가 나란히 있어도 같아 보이지 않습니다.

**그런데 왜 흩어지지 않나.** 잡지의 특집면은 특집마다 색과 서체를 바꾸면서도
한 권으로 읽힙니다. 판형·기사 순서·이름 표기가 같기 때문입니다.
여기서 그 역할을 하는 것이 **정보 순서와 결정 대장**입니다.
게다가 이 페이지들은 항상 같은 바탕화면 위, 같은 창틀 안에서 열립니다 —
창 밖의 틀이 늘 같으니 창 안이 달라도 됩니다.

## 3. ① 히어로 장치 — 다섯 중 하나

첫 화면은 **이 프로젝트에서 가장 특징적인 것**이어야 합니다.
큰 숫자 + 작은 라벨 + 그라디언트는 어느 프로젝트에나 맞는 답이라 아무 말도 하지 않습니다.

| 코드         | 장치       | 언제 쓰나                                    | 예                                                    |
| ------------ | ---------- | -------------------------------------------- | ----------------------------------------------------- |
| **H-CLAIM**  | 명제형     | 상식과 어긋나는 한 문장이 있을 때            | 윷놀이 — "서버를 두지 않았습니다. DB가 서버입니다"    |
| **H-NUMBER** | 수치형     | 숫자 하나가 전부를 설명할 때                 | 정산 배치 — "300만 건 / 12분"                         |
| **H-BEFORE** | 대비형     | 바꾸기 전후가 극명할 때                      | 게이트웨이 — "같은 필터 6벌 → 1벌"                    |
| **H-DIAGRAM**| 도해형     | 구조 자체가 자랑거리일 때                    | 이벤트 흐름 · 파티셔닝                                |
| **H-LIVE**   | 실물형     | 만든 것이 눈에 보이고 만질 수 있을 때        | 게임 판 · 시각화                                      |

**규칙**

- 한 페이지에 **하나만** 씁니다. 명제와 큰 숫자를 같이 쓰면 둘 다 죽습니다
- 명제는 **28자 안쪽**. 두 줄로 끊어 읽히는 길이입니다
- 히어로에 링크 버튼을 두지 않습니다. 아직 읽을 이유를 안 줬습니다

## 4. ② 증거 블록 — 여섯 중 하나(많아야 둘)

포트폴리오의 문장은 전부 자기 주장입니다. **주장 옆에 검증 가능한 것을 하나 둡니다.**
프로젝트마다 검증 가능한 것의 종류가 다르므로 여기서 성격이 크게 갈립니다.

| 코드          | 증거          | 언제 쓰나                        | 주의                                              |
| ------------- | ------------- | -------------------------------- | ------------------------------------------------- |
| **E-RUN**     | 눌러서 실행   | 배포된 웹이 있을 때              | **자동 로드 금지.** 누르기 전에는 통신 없음       |
| **E-MEASURE** | 계측 표       | 성능·부하를 실제로 쟀을 때       | 측정 조건을 반드시 같이 적음. 조건 없는 수치는 거짓말 |
| **E-DIAGRAM** | 구조도        | 흐름이 말보다 그림일 때          | SVG 로 직접. 이미지 파일 금지(docs/04)            |
| **E-CODE**    | 코드 한 조각  | 인터페이스 설계가 핵심일 때      | 20줄 이내. 길면 저장소를 보라고 하는 게 낫습니다  |
| **E-LOG**     | 기록·타임라인 | 오래 이어온 것이 자랑일 때       | 커밋 그래프 · 오답 노트 추이                      |
| **E-SHOT**    | 화면          | 사내 시스템이라 열 수 없을 때    | **최후의 수단.** 스크린샷은 아무것도 증명 못 함   |

**규칙**

- `live` 주소가 있으면 **E-RUN 이 1순위**입니다. 진짜가 있는데 그림을 보여줄 이유가 없습니다
- E-SHOT 만 있는 페이지는 설득력이 가장 낮습니다. 그런 프로젝트일수록 결정 대장을 두껍게 씁니다
- 증거는 결정 대장 **앞**에 옵니다. 먼저 만져 보고 그다음 왜 그렇게 만들었는지 읽는 순서입니다

## 5. ① 그 사이트의 옷 — 팔레트 한 벌

`projects.ts` 의 `theme` 이 인라인 CSS 변수로 들어갑니다.
**색은 지어내지 않습니다.** 그 사이트가 실제로 쓰는 값을 가져옵니다 —
저장소의 디자인 규칙 파일, 앱 아이콘, 운영 사이트 화면 순으로 찾습니다.

| 토큰                 | 무엇                                    |
| -------------------- | --------------------------------------- |
| `mode`               | `dark` / `light` — 밝기 방향            |
| `bg`                 | 바탕                                    |
| `surface`            | 카드 · 패널                             |
| `sunken`             | 한 겹 눌린 곳 (버린 길 · 주소 표시줄)   |
| `fg` `mid` `dim`     | 글자 세 단계                            |
| `line`               | 테두리                                  |
| `accent` `onAccent`  | 강조색과 그 위 글자                     |
| `drop`               | 버린 길                                 |
| `display`            | `gothic` / `serif` — 표제 폰트          |
| `radius`             | 모서리                                  |

**규칙**

- **강조색은 한 페이지에 하나.** 두 번째 색은 `drop`(버린 길)뿐입니다
- 대비 4.5:1 이상. 밝은 사이트의 어두운 강조색은 그대로 쓰고,
  어두운 사이트의 어두운 강조색은 그 사이트의 **다크모드 값**을 찾아 씁니다
- 밝은 화면에서는 카드를 밝기로 띄울 수 없습니다 → 옅은 그림자로 (CSS 가 처리)
- 목록에서 이웃한 프로젝트끼리 비슷한 팔레트를 쓰지 않습니다

**실제 적용 예**

| 프로젝트   | 어디서 가져왔나                                            |
| ---------- | ---------------------------------------------------------- |
| 윷놀이     | 앱 아이콘(`icon-192.png`)의 남색 바탕 + 가운데 방의 청록   |
| 인터페이퍼 | 저장소 `CLAUDE.md` 의 디자인 규칙(회백·흰 카드·차콜·명조) |

> `Project.color` 는 목록 밴드에도 쓰이는 값이라 그대로 둡니다.
> `theme.accent` 와 같게 맞춰 두면 목록에서 누른 것과 열린 페이지가 이어집니다.

## 6. ④ 수치 다섯 개 — 고정 항목이 아닙니다

시안에는 `LANGUAGE / COMMITS / BUILD STEP / 월 운영비 / 기간` 이 들어 있지만
**이건 윷놀이에서 자랑할 것을 고른 결과**이지 모든 프로젝트의 항목이 아닙니다.

| 프로젝트 성격 | 고를 만한 수치                                        |
| ------------- | ----------------------------------------------------- |
| 무료로 만든 것 | 월 운영비 · 빌드 단계 · 소스 파일 수                  |
| 성능을 잰 것  | 처리 건수 · 소요 시간 · 개선 폭 · 측정 횟수           |
| 오래 한 것    | 기간 · 커밋 · 문제 수 · 재풀이 횟수                   |
| 남이 쓴 것    | 붙은 서비스 수 · 버전 수 · 릴리스 주기                |

**규칙**

- **다섯 개.** 넷이면 허전하고 여섯이면 안 읽습니다
- **0 을 두려워하지 않습니다.** "빌드 단계 0", "월 운영비 0원" 은 강한 수치입니다
- 스타 수는 **넣지 않습니다.** 0 이면 초라하고, 많아도 만든 사람의 실력과 무관합니다
- 지어내지 않습니다. 근거는 저장소·README·직접 잰 값뿐입니다

## 7. 고정 — 여기는 프로젝트마다 바꾸지 않습니다

### 7.1 타이포

기존 상세페이지가 "딱딱하고 작고 얇다"고 지적받은 원인이 여기 있었습니다.
`globals.css` 의 `font-weight: 300` 이 본문까지 내려와 있었습니다.

| 자리          | 크기                  | 굵기 | 비고                       |
| ------------- | --------------------- | ---- | -------------------------- |
| 히어로        | clamp(38, 7.4vw, 82)  | 900  | 세 줄 이내                 |
| 섹션 제목     | clamp(27, 3.6vw, 38)  | 900  |                            |
| 리드 문장     | 18.5                  | 400  | 56자 이내                  |
| **본문**      | **17 이상**           | 400  | **300 을 쓰지 않습니다**   |
| 카드 제목     | 19.5                  | 700  |                            |
| 라벨 · 수치   | 11.5–13               | 400  | 등폭(IBM Plex Mono)        |

- 본문 행간 **1.75 이상**, 한 줄 **56자 이내**
- 한글은 단어 안에서 줄이 바뀝니다 → 제목에 `word-break: keep-all` 필수

### 7.2 결정 대장

이 사이트의 상세페이지가 남들과 다른 유일한 지점입니다. **빼지 않습니다.**

- 결정 **2~6개**. 하나면 대장이 아니고, 일곱이면 안 읽습니다
- 각 결정은 `질문 / 버린 길+왜 / 택한 길+왜` 세 조각이 **전부 있어야** 합니다
- **버린 길이 없으면 그건 결정이 아니라 기능입니다.** 기능은 "만든 것"으로 내립니다
- 버린 이유는 "안 좋아서"가 아니라 **구체적 손해**로 적습니다
  (`무료 플랜에서는 잠들거나 돈이 듭니다` ← 좋음 / `비효율적입니다` ← 나쁨)

### 7.3 마무리 두 칸

- **배운 것** — 한 단락. 다음에 비슷한 걸 만들 때 먼저 던질 질문
- **아직 못 한 것** — 목록. 잘한 것만 적힌 포트폴리오보다 한계를 아는 사람이 믿음직합니다
  - "아쉬운 것"이 아니라 **"아직 못 한 것"** 입니다. 사과가 아니라 현재 상태 보고입니다

### 7.4 품질 바닥

전 페이지가 지킵니다. 시안에 이미 들어 있습니다.

- 모바일 폭까지 무너지지 않음 (820px 에서 결정 대장이 한 줄로 접힘)
- 키보드로 전부 도달 · 포커스 링이 어두운 바탕에서 보임
- `prefers-reduced-motion` 에서 등장 애니메이션과 선 그리기가 즉시 완료
- 이미지 파일 0개. 도해는 SVG (docs/04)
- 상세페이지는 **정적 렌더링을 유지**합니다 (docs/03 §3.1)

| -------- | ---------------------------------------------------------------------- |
| E-RUN    | 01·02·03·05 — 열면 바로 동작하는 것이 있습니다                        |
| E-DIAGRAM| 04 — 로그인 벽 뒤라 열어도 로그인 화면뿐입니다                        |
| E-CODE   | 06 — 접근 제어 전부가 SQL 열세 줄입니다. 그 줄이 곧 설계입니다        |

**코드를 지어내지 않습니다.** 06 의 조각은 `supabase/schema.sql` 에서 그대로 옮겼습니다.
20줄을 넘기면 저장소를 보라고 하는 편이 낫습니다.

**04 와 05 는 둘 다 밝고 따뜻한데도 붙어 보이지 않습니다.** 04 는 흰 바탕에 분홍,
05 는 **차가운 식판 회녹색 바탕에 따뜻한 종이 카드**입니다. 바탕과 카드의 온도가
반대라 인상이 갈립니다. 팔레트를 고를 때 강조색만 보지 말고 바탕·카드 조합을 봅니다.

### 04 에서 두 규칙이 또 부딪쳤습니다 (2026-07-30)

**증거.** MomsUp 은 랜딩을 빼면 전부 로그인 뒤입니다. `눌러서 실행`을 걸면
방문자에게 보이는 건 **로그인 화면 하나**입니다. 그건 증거가 아니라 문 앞 사진이라,
§4 의 "live 가 있으면 E-RUN 1순위"를 여기서는 접고 **E-DIAGRAM** 으로 갔습니다.
→ 규칙을 고칩니다: **`live` 가 있어도 로그인 벽 뒤면 E-RUN 을 쓰지 않습니다.**

**히어로.** 01 과 04 가 둘 다 명제형입니다. 억지로 수치형을 쓰려다 보니
내세울 숫자가 없어 "큰 숫자 + 작은 라벨" 이라는 아무 말도 안 하는 히어로가 나왔습니다.
**장치를 돌려쓰려고 없는 근거를 만들지 않습니다.** 대신 01 과 04 는
목록에서 붙어 있지 않고, 증거·색·모서리가 다릅니다.

**연달아 같은 조합을 쓰지 않습니다.** 목록에서 이어서 눌러 보는 사람에게
같은 페이지를 두 번 보여주는 셈이 됩니다.

### 증거가 겹칠 때는 히어로를 바꿉니다 (2026-07-30)

01 과 02 는 **둘 다 배포된 웹**입니다. §4 의 "live 주소가 있으면 E-RUN 이 1순위"와
"같은 조합을 연달아 쓰지 않는다"가 부딪칩니다.

**증거를 양보하지 않습니다.** 진짜가 있는데 스크린샷을 보여주는 것은
페이지를 다르게 만들려고 설득력을 깎는 일입니다. 대신 **히어로를 바꿉니다** —
01 은 명제형, 02 는 대비형이라 첫 화면에서 이미 다른 페이지로 읽힙니다.

앞으로도 이 순서로 풉니다. ① 증거는 그 프로젝트에 가장 강한 것으로 고정
② 히어로로 차이를 냄 ③ 그래도 겹치면 그때 증거를 다시 봅니다.

## 9. 데이터 모델 — 가이드를 코드로 옮기면

지금 `Project` 타입은 시안 A 를 담지 못합니다. 이렇게 바꿉니다.

| 지금            | 바뀜                                    | 이유                                        |
| --------------- | --------------------------------------- | ------------------------------------------- |
| —               | `theme: ProjectTheme`                   | §5. 그 사이트의 팔레트 한 벌                |
| —               | `hero: Hero`                            | §3 의 장치. 명제·대비가 각자 필드를 가짐    |
| —               | `evidence: Evidence`                    | §4 의 여섯 중 하나                          |
| —               | `facts: {label, value, note?}[]`        | §6. 고정 항목이 아니라 프로젝트가 고름      |
| `questions[]`   | `decisions: {ask, dropped, taken}[]`    | 버린 길이 타입에 **강제**됩니다             |
| `did[]`         | `built: {title, body}[]`                | 문자열에 `<b>` 를 섞던 것을 구조로          |
| `regret`        | `limits: string[]`                      | 한 단락 → 목록                              |
| `meta`          | 유지                                    | 저장소 사실. `facts` 는 이 중에서 골라 씁니다 |

`decisions` 에서 `dropped` 를 **필수**로 두는 것이 이 모델의 핵심입니다.
버린 길을 적을 수 없으면 그 항목은 결정이 아니고, 타입이 그걸 잡아 줍니다.

## 10. 저장소를 새로 받으면 하는 일

1. 저장소와 운영 사이트에서 **실측** — 언어 · 커밋 · 기간 · 라이선스 · 배포 주소
2. README 를 읽고 **결정 2~6개**를 뽑는다. 버린 길이 안 나오면 물어본다
3. **그 사이트의 팔레트를 찾는다** (§5) — 디자인 규칙 파일 · 앱 아이콘 · 실제 화면 순
4. §8 조합표에서 **히어로와 증거를 고른다.** 앞 프로젝트와 겹치지 않게
5. **수치 다섯 개**를 고른다 (§6)
6. **아이콘** — 그 사이트의 파비콘·앱 아이콘을 옮긴다.
   없으면 그 사이트의 **시그니처 화면**을 그린다 (예: 인터페이퍼의 Coverflow)
7. `projects.ts` 에 항목을 쓰고 `desktop: true` · `icon` 을 켠다
8. 바탕화면에 아이콘이 하나 늘어난다. **화면 코드는 건드리지 않는다**

> **지어내지 않습니다.** 1인칭 회고("그때 이런 생각을 했다")는 근거가 있을 때만 씁니다.
> 근거가 없으면 §9 TODO 에 질문으로 남기고 비워 둡니다.
> 예시로 채운 값이 배포되면 그건 거짓말입니다 — 지금 `yutnori` 를 뺀 11개가 그 상태입니다.
